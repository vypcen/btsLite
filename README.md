# BlackCat Testing Community

Community — редакция для небольших команд. В одной установке доступны **5 мест для активных пользователей**, включая администраторов, тестировщиков, разработчиков и наблюдателей.

В Community доступны тест-кейсы и чек-листы, планы и прогоны, баги, вложения, основные отчёты, CI и интеграции с трекерами, 2FA, аудит и резервные копии. В Enterprise входят корпоративный SSO, пользовательские роли, обязательное ревью, матрицы конфигураций, спринты, расчёт готовности релиза, ИИ-помощник и специализированный импорт из Test IT.

Для параллельной установки используйте отдельную базу и том вложений. Docker Compose выбирает проект `blackcat-testing-lite` и порт `3002`. Для переноса из другой редакции выгрузите проект в JSON и импортируйте его в чистую установку.

Система управления тестированием: проекты, тест-кейсы, тест-прогоны, баг-репорты и вложения. Изменения сразу видны всем участникам.

**Документация:** [руководство пользователя](docs/USER_GUIDE.md) · [руководство администратора](docs/ADMIN_GUIDE.md) · [план пилота](docs/PILOT.md) · [API](docs/API.md) · [изменения версий](CHANGELOG.md). Та же документация открывается в самом приложении кнопкой «Справка».

- **Тест-кейсы** со статусом готовности (черновик / готов / устарел) и последним результатом из прогонов. Кейсы раскладываются по вложенным папкам, перемещаются пачкой, а в прогон папку можно добавить целиком.
- **Чек-листы** — второй вид тест-кейса: вместо шагов список коротких проверок, на вкладке кейсов они идут отдельным блоком. Пункты можно отмечать выполненными прямо в чек-листе, а в прогоне каждый пункт отмечается отдельно: итог считается сам, виден регресс по пунктам, баг заводится прямо из упавшего пункта.
- **Импорт и экспорт тест-кейсов** в CSV: кнопки «Импорт» и «Экспорт» в разделе кейсов. Файл открывается в Excel и Google Таблицах; при импорте сначала показывается, что будет создано и обновлено, а понимаются в том числе выгрузки TestRail и Qase.
- **Тест-прогоны**: набор кейсов, проверяемый на конкретной сборке. Результаты прошлых прогонов не перезаписываются, а в прогоне видно, что было с каждым кейсом в прошлый раз, и отмечены регрессы.
- **Баги** с жизненным циклом Новый → В работе → Исправлен → Проверен → Закрыт (плюс «Отклонён» и «Дубликат»), серьёзностью, исполнителем и окружением. Из упавшего кейса в прогоне баг заводится одной кнопкой, шаги и ожидаемый результат подставляются сами.
- **Комментарии** к багам и тест-кейсам: их пишут все участники проекта, в том числе разработчики.
- **Вложения** (скриншоты, логи) к багам и к результатам в прогонах: можно перетащить файл или вставить скриншот через Ctrl+V.
- **Автотесты**: каждый запуск автотестов (на своём компьютере или в CI) попадает отдельной папкой во вкладку «Автотесты» с результатами и скриншотами падений. Тесты сами заводятся в реестре при первой встрече. Подробнее в части 3.

## Часть 1. Развернуть на своём компьютере

### Шаг 1. Установить Docker и Git

| ОС | Docker | Git |
|---|---|---|
| **Windows 10/11** | [Docker Desktop](https://www.docker.com/products/docker-desktop/). При установке оставьте галочку «Use WSL 2». После установки перезагрузите компьютер. | [git-scm.com](https://git-scm.com/download/win) |
| **macOS** | [Docker Desktop](https://www.docker.com/products/docker-desktop/) (выберите Apple Silicon или Intel) | `xcode-select --install` |
| **Linux (Ubuntu/Debian)** | `curl -fsSL https://get.docker.com \| sh`, затем `sudo usermod -aG docker $USER` и перелогиньтесь | `sudo apt install git` |

Проверка в терминале (на Windows — PowerShell):

```sh
docker --version
docker compose version
git --version
```

Все три команды должны вывести версии. На Windows и macOS Docker Desktop должен быть запущен (иконка кита в трее).

### Шаг 2. Получить код

```sh
git clone https://github.com/vypcen/btsLite.git
cd btsLite
```

Файл `import/export.json` с данными из прошлой версии в репозиторий не попадает (в нём хэши паролей). Если нужен импорт, скопируйте его на второй компьютер в папку `import/` вручную.

### Шаг 3. Создать файл настроек `.env`

```sh
# Linux / macOS
cp .env.example .env
# Windows (PowerShell)
Copy-Item .env.example .env
```

Откройте `.env` в блокноте и замените `POSTGRES_PASSWORD` на длинный случайный пароль. Сгенерировать можно так:

```sh
# Linux / macOS
openssl rand -base64 24
# Windows (PowerShell)
[Convert]::ToBase64String((1..24 | % { Get-Random -Max 256 }))
```

Важно: пароль базы задаётся **один раз** при первом запуске. Если поменять его потом, приложение не подключится к уже созданной базе.

### Шаг 4. Запустить

В папке проекта:

```sh
docker compose up -d --build
```

Первый запуск занимает 1–3 минуты: скачиваются образы Node.js и PostgreSQL. Проверьте, что всё поднялось:

```sh
docker compose ps
docker compose logs app
```

В логах должна быть строка `BlackCat Testing Community <версия> запущен: http://localhost:3002`.

### Шаг 5. Открыть приложение

Откройте в браузере **http://localhost:3002** и зарегистрируйте первого пользователя — он станет администратором. Для этого нужен **код установки**: сервер печатает его в логах при первом запуске с пустой базой.

```sh
docker compose logs app | grep "Код"
# [server] Пользователей ещё нет. Код для регистрации первого администратора: 3f9c1a7b2e44
```

Код защищает свежую установку: если адрес уже открыт наружу, посторонний не сможет зарегистрироваться первым и стать администратором. Код можно задать заранее в `.env` (`SETUP_CODE=...`).

Остальных пользователей администратор заводит в разделе **«Пользователи» → «+ Новый пользователь»**, или они регистрируются сами, если регистрация открыта (`REGISTRATION=open`). По умолчанию самостоятельная регистрация закрыта.

### Шаг 6. Перенести данные из прошлой версии (необязательно)

Если файл `import/export.json` на месте:

```sh
docker compose exec app node scripts/import.js import/export.json
```

Импортируются пользователи, проекты и тест-кейсы. Старые пароли продолжат работать (при первом входе они автоматически перехэшируются в bcrypt). Повторный запуск безопасен: уже существующие записи пропускаются.

### Шаг 7. Автозапуск после перезагрузки

Контейнеры настроены с `restart: unless-stopped`: они поднимаются сами, когда запускается Docker.

- **Windows/macOS:** в Docker Desktop → Settings → General включите «Start Docker Desktop when you sign in». Настройте автоматический вход в учётную запись или не выходите из неё.
- **Linux:** `sudo systemctl enable docker`.
- **Везде:** отключите спящий режим (Windows: Параметры → Система → Питание; macOS: Настройки → Аккумулятор/Энергосбережение → «Не переходить в режим сна»). Пока компьютер спит, приложение недоступно.

### Шаг 8. Резервные копии

Проще всего — в интерфейсе: **«Пользователи → Резервные копии»**. Приложение само делает копию раз в сутки (база и вложения, с проверкой), хранит последние 14 в папке `backups/` рядом с проектом; там же кнопки «Создать сейчас» и «Скачать». Восстановление:

```sh
docker compose stop app
docker compose run --rm -v "$PWD/backups:/backups" app node scripts/backup.js restore /backups/testball-ГГГГММДД-ЧЧММСС.tar --yes
docker compose start app
```

На Linux папку для копий создайте заранее и отдайте пользователю контейнера: `mkdir -p backups && sudo chown 1000:1000 backups` (на macOS и Windows не нужно). Подробности и настройки — [руководство администратора](docs/ADMIN_GUIDE.md#резервное-копирование-и-восстановление).

Без интерфейса — скриптом:

```sh
# Linux / macOS
./scripts/backup.sh
# Windows
powershell -ExecutionPolicy Bypass -File scripts\backup.ps1
```

В папке `backups/` появятся дамп базы и архив вложений, хранятся последние 14 копий. Чтобы делать это каждую ночь:

- **Linux/macOS:** `crontab -e` и строка `0 3 * * * cd /путь/к/btsLite && ./scripts/backup.sh`
- **Windows:** Планировщик заданий → Создать простую задачу → Ежедневно → Запуск программы `powershell`, аргументы `-ExecutionPolicy Bypass -File C:\btsLite\scripts\backup.ps1`.

Хорошо бы время от времени копировать папку `backups/` на другой диск или в облако.

Восстановление из копии:

```sh
gunzip -c backups/testball-ГГГГ-ММ-ДД_ЧЧ-ММ.sql.gz | docker compose exec -T db psql -U testbed testbed
```

(на Windows: `Get-Content backups\файл.sql | docker compose exec -T db psql -U testbed testbed`). Восстанавливать лучше в пустую базу.

Вложения восстанавливаются отдельно:

```sh
# Linux / macOS
docker compose exec -T app tar -xzf - -C /app/data < backups/uploads-ГГГГ-ММ-ДД_ЧЧ-ММ.tar.gz
# Windows
docker compose cp backups\uploads-ГГГГ-ММ-ДД_ЧЧ-ММ\. app:/app/data/uploads
```

### Полезные команды

| Что сделать | Команда |
|---|---|
| Посмотреть логи | `docker compose logs -f app` |
| Остановить | `docker compose stop` |
| Запустить снова | `docker compose start` |
| Обновить до новой версии | резервная копия, `git pull`, `docker compose up -d --build` — подробно в [docs/UPGRADE.md](docs/UPGRADE.md) |
| Зайти в базу через psql | `docker compose exec db psql -U testbed testbed` |
| Удалить всё **вместе с данными и вложениями** | `docker compose down -v` (осторожно!) |

### Разработка интерфейса

Интерфейс живёт в `web/` (React + TypeScript + Vite). В Docker он собирается автоматически. Для разработки с мгновенной перезагрузкой страницы:

```sh
docker compose up -d             # сервер и база
npm --prefix web install
npm run dev:web                  # http://localhost:5173, запросы /api уходят на localhost:3000
```

Чтобы собрать интерфейс без Docker (например, для `node server/index.js`), выполните `npm run build:web`: результат появится в `public/`.

## Часть 2. Доступ к приложению извне

По умолчанию приложение принимает соединения только с компьютера, на котором запущено. Для доступа команды настройте обратный прокси с HTTPS. Для доступа внутри доверенной сети можно задать `APP_BIND=0.0.0.0` и `TRUST_PROXY=false` в `.env`.

## Часть 3. Автотесты

При запуске из интерфейса по `TESTBALL_RUN` репортёр Playwright возвращает ошибку CI, если не удалось передать результаты. Для запуска без номера тот же режим включает `TESTBALL_REQUIRE_UPLOAD=1`.

Каждый запуск автотестов становится отдельной «папкой» во вкладке проекта **Автотесты**. В папке видно, что прошло, что упало, что сломалось или пропущено, текст ошибки, стектрейс, скриншоты и что было с тестом в прошлом запуске. Автотест заводится в реестре («Автотесты» → «Все автотесты») один раз, при первой встрече, и дальше узнаётся по набору и названию. Раздел тест-кейсов это не засоряет.

### Как подключить Playwright

1. Во вкладке «Автотесты» нажмите **Подключить автотесты** и создайте токен. Токен показывается один раз. Он годится только для отправки результатов: читать или менять баги и кейсы с ним нельзя. Каждому участнику лучше завести свой токен, тогда в запуске видно, кто его отправил.
2. Положите репортер рядом с `playwright.config` (его можно закоммитить):
   ```sh
   curl -o testball-reporter.js http://localhost:3002/testball-reporter.js
   ```
3. Добавьте его в `playwright.config`:
   ```js
   reporter: [["list"], ["./testball-reporter.js"]],
   use: {
     screenshot: "only-on-failure",   // скриншот упавшего теста
     trace: "retain-on-failure",      // трейс упавшего теста (открывается на trace.playwright.dev)
   },
   ```
4. Задайте настройки и запускайте тесты как обычно:
   ```sh
   export TESTBALL_URL=http://localhost:3002
   export TESTBALL_TOKEN=tb_...
   export TESTBALL_PROJECT=LK
   npx playwright test
   ```
   В Windows PowerShell: `$env:TESTBALL_TOKEN="tb_..."`. Если переменные не заданы, репортер молча выключается: у коллег без токена и в CI без настроек тесты работают как обычно. Если BlackCat Testing недоступен, репортер пишет одно предупреждение и тесты не прерывает.

Необязательные переменные: `TESTBALL_TITLE` (название запуска, по умолчанию «Локальный запуск <адрес проверяемого сайта>», например «Локальный запуск staging.example.com»; ветка показывается в описании запуска), `TESTBALL_ENV` (окружение, например `RC`), `TESTBALL_APP_URL` (адрес тестируемого приложения, по умолчанию `baseURL` из конфига), `TESTBALL_BUILD` (по умолчанию короткий хэш коммита), `TESTBALL_BRANCH`. Окружение и адрес можно передать и опциями репортера, взяв из своих переменных: `["./testball-reporter.js", { appUrl: process.env.WEB_URL }]`.

В шапке запуска видно, что запускали (только проекты Playwright, которые реально выполнялись, с учётом `--project`), окружение и адрес приложения.

Шаги `test.step` уходят вместе с результатом, включая шаги из `beforeEach`. В результате видно, какие шаги прошли, сколько заняли и на каком тест упал; в списке запуска у упавшего теста написано «Упал на шаге: …», а «Завести баг» подставляет шаги в баг-репорт. В реестре («Все автотесты») у теста хранится список шагов из последнего прохождения.

Что попадает в папку запуска:

| Статус | Когда |
|---|---|
| Пройден | тест прошёл. Если со второй попытки (`retries`), рядом пометка «Нестабильный» |
| Упал | не прошла проверка `expect` |
| Сломан | таймаут теста или исключение в самом тесте |
| Пропущен | `test.skip` / `test.fixme`, а также тесты, до которых не дошла очередь (`--max-failures`, Ctrl+C) — с пометкой «Не выполнялся» |

Проекты Playwright (`chromium`, `mobile`…) считаются разными тестами: набор выглядит как `[mobile] login.spec.ts`. При повторах учитывается итоговая попытка, файлы прикладываются от неё же.

### Другие фреймворки: отчёт JUnit XML

pytest, Jest, Cypress, JUnit и другие умеют писать отчёт JUnit XML (для TestNG и NUnit есть свой формат — раздел «Selenium» ниже). Его отправляет скрипт `report.js` (нужен Node.js 20+):

```sh
curl -O http://localhost:3002/report.js
node report.js results/junit.xml                                 # готовый отчёт
node report.js results/ -- pytest --junitxml=results/junit.xml   # запустить и отправить
```

С `--` скрипт сначала выполняет команду, затем отправляет только свежие отчёты и завершается с кодом самой команды. Настройки те же переменные `TESTBALL_*` или параметры `--url`, `--token`, `--project`, `--title`, `--build`, `--env`, `--branch`; справка — `node report.js --help`.

Скриншоты прикладываются к упавшим тестам, если отчёт ссылается на них строкой `[[ATTACHMENT|путь]]` в выводе теста или свойством `<property name="attachment" value="путь"/>`. Пути считаются от папки с отчётом или от текущей папки. Для pytest это делается в `conftest.py`:

```python
import os, pytest

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    rep = (yield).get_result()
    if rep.when == "call" and rep.failed:
        page = item.funcargs.get("page") or item.funcargs.get("driver")
        if page:
            os.makedirs("results/screenshots", exist_ok=True)
            path = f"results/screenshots/{item.name}.png"
            page.screenshot(path=path) if hasattr(page, "screenshot") else page.save_screenshot(path)
            item.user_properties.append(("attachment", path))  # попадёт в отчёт как <property name="attachment">
```

### Selenium

Selenium сам отчётов не пишет: результаты сохраняет тестовый фреймворк, который его запускает. `report.js` понимает отчёты всех популярных связок — команды для каждой есть во вкладке «Автотесты → Подключить → Selenium».

| Связка | Что отправлять | Номер кейса | Скриншот упавшего теста |
|---|---|---|---|
| Java + TestNG | `node report.js target/surefire-reports/ -- mvn test` (берётся `testng-results.xml`) | `@Test(description = "LK-12 Вход")` | `Reporter.log("[[ATTACHMENT|путь]]")` |
| Java + JUnit 5 | `node report.js target/surefire-reports/ -- mvn test` (Gradle — `build/test-results/test/`) | `@DisplayName("LK-12 Вход")` (у Surefire включите `usePhrasedTestCaseMethodName`) или Allure `@TmsLink("LK-12")` | `System.out.println("[[ATTACHMENT|путь]]")` |
| Python + pytest | `node report.js results/ -- pytest --junitxml=results/junit.xml` | `record_property("testball", "LK-12")` | `print("[[ATTACHMENT|путь]]")` при `junit_logging = system-out` или `conftest.py` выше |
| C# + NUnit | `dotnet test --logger "nunit;LogFilePath=results/TestResult.xml"`, затем `node report.js results/TestResult.xml` (пакет NunitXml.TestLogger) | `[Description("LK-12")]` или `[Category("LK-12")]` | `TestContext.AddTestAttachment(путь)` |

Что переносится из **TestNG**: статусы (упавшая проверка — «Упал», исключение Selenium вроде `NoSuchElementException` — «Сломан»), повторы `RetryAnalyzer` (пометка «нестабильный»), параметры `@DataProvider` в названии, `Reporter.log`, упавшие `@BeforeMethod`/`@BeforeClass` — отдельной записью «[настройка] …», чтобы было видно, почему тесты пропущены. В папке Surefire рядом с `testng-results.xml` лежат те же тесты в JUnit-формате (`TEST-*.xml`) — они пропускаются, чтобы не было дублей.

Из **NUnit 3** (`TestResult.xml`): статусы (`Failed` с меткой `Error` — «Сломан»), причина пропуска, вывод теста, вложения `TestContext.AddTestAttachment`.

Selenium можно подключить и через Allure (allure-testng, allure-junit5, allure-pytest) — см. ниже.

### Allure: allure-results

Если тесты уже пишут результаты Allure (allure-pytest, allure-junit5, allure-testng, allure-js для Playwright/Jest/Cypress, allure-kotlin), достаточно отправить папку:

```sh
node report.js allure-results/                                     # готовые результаты
node report.js allure-results/ -- pytest --alluredir=allure-results  # запустить и отправить
```

Переносятся шаги (с вложенными), ошибка и стектрейс, вложения (к упавшим тестам; `--attach-all` — ко всем), параметры, повторы (retries → пометка «нестабильный»). Связь с ручным кейсом — меткой `@allure.label("testball", "LK-12")` или ссылкой `@allure.testcase("LK-12")`.

### Что важно знать

- Тест узнаётся по набору (`classname`) и названию. Переименованный тест заведётся как новый; старый можно удалить из реестра кнопкой ✕.
- **Связь с ручным кейсом** ставится сама, если в названии теста или набора есть номер кейса: `test("вход по паролю @LK-12")` или `test_login[LK-12]` (а вот `test_login_LK_12` не распознается). В Playwright можно тегом: `test("вход", { tag: "@LK-12" }, …)`, в Allure — меткой `testball`. Связь, выбранную вручную во «Все автотесты», отчёт не меняет.
- Если тест встретился в отчёте дважды (перезапуск упавшего), в папке остаётся последний результат.
- Файлы больше `MAX_UPLOAD_MB` (по умолчанию 20 МБ) не прикладываются — обычно это длинные видео. Видео (`video: "retain-on-failure"`) прикладывается, если влезает.
- Своя интеграция без готовых скриптов: `POST /api/projects/<KEY>/autoruns` → `POST …/autoruns/<num>/results` (пачками до 1000) → скриншоты `POST …/results/<id>/attachments` → `PATCH …/autoruns/<num>` с `{"state":"finished"}`, всё с заголовком `Authorization: Bearer <токен>`. Все поля и примеры — в [docs/API.md](docs/API.md#автотесты).

## Часть 4. Возможности и ограничения Community

В одной установке Community доступно до двух активных проектов. Создание, импорт и восстановление занимают по одному месту. Перенос проекта в корзину освобождает место. Если до обновления было больше двух проектов, данные сохраняются, и для добавления нового нужно освободить место. Установку через Docker Compose можно подключить к трекеру, CI и получателям вебхуков.

### Kubernetes (Helm)

Community устанавливается через Docker Compose. Развёртывание в Kubernetes и несколько реплик относятся к Enterprise.

### Единый вход: OpenID Connect, LDAP / AD, Kerberos

В Community пользователи входят по логину и паролю. Доступна двухфакторная аутентификация.

### Роли и лицензии

Community включает пять мест. Активный пользователь занимает одно место независимо от роли и числа проектов. Блокировка или удаление освобождает место. Используйте встроенные роли «Администратор», «Тестировщик», «Разработчик» и «Наблюдатель». Роль может различаться по проектам.

### Версии тест-кейсов

Каждая правка содержимого кейса создаёт новую версию: название, шаги, ожидаемый результат, приоритет, статус. Перенос кейса в другую папку и отметки пунктов чек-листа версию не создают. В карточке кейса есть история с разницей между версиями и кнопка «Вернуть». Возврат не стирает историю, а создаёт новую версию со старым содержимым.

Прогон помнит, какую версию кейса проверяли. Если кейс изменили позже, в результате показан текст проверенной версии и пометка, что кейс с тех пор менялся. Если двое правят кейс одновременно, второй получает предупреждение, а не молча затирает правку первого.

### Требования и трассировка

Вкладка «Требования» в проекте: требования из ТЗ, Jira или Confluence, связанные с тест-кейсами. Для каждого требования видно покрытие — «не покрыто», «не проверено», «провалено», «частично», «пройдено» (по последним результатам кейсов) — и открытые баги по его кейсам. Вверху — сколько требований покрыто тестами.

- Требования заводятся вручную или импортируются из CSV (выгрузка Jira, Excel). Повторный импорт обновляет требования с тем же ключом (`AUTH-1`), поэтому выгрузку можно подтягивать регулярно.
- Кейсы связываются в форме требования; в карточке кейса видно, какие требования он проверяет.
- «Матрица покрытия» — сетка «требования × кейсы» с результатами (последними, в релизе или в прогоне) и выгрузкой в Excel, PDF и CSV для отчёта заказчику или аудитору.

### Тест-планы, динамические наборы, блокировка

Тест-план — это набор кейсов для проверки (вкладка «Тест-планы»):

- **Статический план** — кейсы выбраны вручную.
- **Динамический план** — кейсы подбираются фильтром: папки, приоритет, статус, вид, текст в названии, наличие автотеста, последний результат. Например, фильтр «Последний результат: Упал» собирает повторную проверку проблемных кейсов. Новые кейсы, подходящие под фильтр, попадают в план сами.
- **Блокировка** фиксирует состав плана и версии кейсов (для динамического плана — снимок на момент блокировки). Заблокированный план нельзя изменить или удалить. Прогоны по нему проверяют зафиксированные версии; их нельзя удалить или дополнить. Кейс из заблокированного плана нельзя удалить. Снять блокировку может тот, кто её поставил, или администратор.
- **Экспорт набора**: CSV (тот же формат, что импорт кейсов, открывается в Excel) или JSON. Для заблокированного плана выгружаются зафиксированные версии.

### Автоматическое распределение по исполнителям

При создании прогона (обычного или по плану) и кнопкой «Распределить» на странице прогона непроверенные кейсы раздаются выбранным тестировщикам. Стратегии:

- **по трудоёмкости** — учитываются число шагов и пунктов, а также работа, уже назначенная исполнителю;
- **по очереди**;
- **по папкам** — папка целиком достаётся одному исполнителю.

В прогоне есть фильтр «Мои кейсы», исполнителя можно сменить вручную в карточке результата. Нагрузка исполнителей видна во вкладке «Аналитика».

### Параметризованные вебхуки

Вкладка «Интеграции» → «Вебхуки». Вебхук срабатывает на события проекта:

- баг создан, изменён или сменил статус;
- прогон создан или закрыт;
- отмечен результат кейса;
- кейс создан, изменён или удалён;
- план заблокирован или разблокирован;
- запуск автотестов начат или завершён;
- автотест стал нестабильным.

URL, заголовки и тело — шаблоны с подстановками `{{bug.title}}`, `{{run.counts.failed}}`, `{{project.key | lower}}` и фильтрами `| json`, `| jsonstr`, `| url`, `| upper`, `| lower`, `| default:"…"`. Условие вида `bug.severity = blocker, critical` ограничивает срабатывание.

Если задан секрет, тело подписывается HMAC-SHA256 в заголовке `X-TestBall-Signature`. Неудачная доставка (сеть, 5xx) повторяется ещё дважды. Журнал доставок хранит запрос и ответ, кнопка «Проверить» отправляет пример события.

Пример для чата (Mattermost, Rocket.Chat, Slack-совместимый):

```json
{"text": "{{title}}: {{bug.id}} «{{bug.title | jsonstr}}» ({{bug.severity}}) {{bug.url}}"}
```

### Трекеры задач

Поддерживаются Jira (Cloud и Server/DC), YouTrack, GitLab, GitHub и Redmine; подключаются во вкладке «Интеграции» → «Трекер задач». В карточке бага можно создать задачу в трекере (шаги, фактический и ожидаемый результат подставятся сами) или привязать существующую по ключу.

Статус задачи обновляется кнопкой и раз в 10 минут в фоне. Закрытая задача переводит баг из «В работе» в «Исправлен» (настройка). Можно включить автосоздание задач для новых багов, в том числе только для выбранных серьёзностей. Токены трекеров хранятся в базе в зашифрованном виде (AES-256-GCM, ключ из `APP_SECRET`).

### Запуск автотестов в CI с параметрами

Вкладка «Интеграции» → «Запуск автотестов в CI»: задача GitLab CI, GitHub Actions, Jenkins или любой HTTP-адрес, плюс набор параметров. У параметра бывают значение по умолчанию, список допустимых значений и признак обязательности. Во вкладке «Автотесты» кнопка **Запустить в CI** создаёт запуск в состоянии «В очереди» и передаёт в CI параметры, а также `TESTBALL_RUN`, `TESTBALL_PROJECT` и `TESTBALL_URL`. Репортеры видят `TESTBALL_RUN` и пишут результаты в этот запуск. Пример для `.gitlab-ci.yml`:

```yaml
e2e:
  rules: [{ if: '$CI_PIPELINE_SOURCE == "trigger" || $CI_PIPELINE_SOURCE == "api"' }]
  script:
    - npx playwright test --project=$BROWSER   # TESTBALL_URL/TOKEN/PROJECT — в переменных CI, TESTBALL_RUN пришлёт BlackCat Testing
```

Для CI лучше заводить **токен проекта** (флажок «только KEY» при создании токена): даже утёкший, он не откроет другие проекты.

### Нестабильные (flaky) автотесты

Нестабильность определяет сервер после каждого завершённого запуска по последним `FLAKY_WINDOW` запускам теста. Признаки:

- тест прошёл с повторной попытки (ретраи Playwright, `rerunFailingTestsCount` Maven Surefire, pytest-rerunfailures);
- на одной сборке тест и проходил, и падал;
- результат часто меняется между «прошёл» и «упал».

Один переход «сломали → починили» — это регресс, а не нестабильность. Нестабильный тест помечается в реестре автотестов с причиной и оценкой, и уходит событие `test.flaky`. Тест можно отправить в карантин и связать с ручным кейсом — тогда кейс засчитывается в покрытие автоматизацией.

### Аналитика

Вкладка «Аналитика» показывает:

- покрытие кейсов проверками и автотестами;
- последние прогоны с процентом прохождения;
- поток багов (заведено и решено по дням);
- открытые баги по серьёзности;
- динамику прохождения автотестов;
- самые падающие и нестабильные тесты;
- нагрузку исполнителей.

Период — от 7 до 365 дней.

### Экспорт, импорт и миграция из других TMS

- **Проект целиком**: вкладка проекта «Настройки» → «Скачать со всеми вложениями» (или без вложений) — JSON с кейсами и историей версий, планами, прогонами, багами (с историей статусов), комментариями, автотестами и, по желанию, вложениями. Загружается в любую установку: «Проекты» → **Импорт** → «BlackCat Testing». Создаётся новый проект с указанным ключом.
- **Миграция из TMS**: «Проекты» → **Импорт** → TestRail (XML), TestLink (XML) или Qase (JSON). Разделы становятся папками, а шаги с ожидаемыми результатами — шагами кейса. Перед созданием проекта показывается, сколько всего будет перенесено.
- **CSV**: импорт кейсов в существующий проект — вкладка «Тест-кейсы» → «Импорт». Понимает выгрузки TestRail и Qase.

## Безопасность в этой версии

- Роли: **тестировщик** работает со своими проектами (создаёт, меняет, удаляет), **разработчик** их просматривает и пишет комментарии, **наблюдатель** только просматривает, **администратор** видит все проекты и в разделе «Пользователи» меняет роли, блокирует и удаляет пользователей, выдаёт доступ к проектам. Проекты, в которые пользователя не добавили, для него не существуют. Права проверяет сервер на каждом запросе, интерфейс лишь прячет недоступные кнопки. Подробно — в [docs/API.md](docs/API.md#роли-и-доступ-к-проектам).
- Первый пользователь в пустой базе становится админом, но только с кодом установки из логов сервера (шаг 5). Дальше пользователей заводит админ или они регистрируются сами разработчиком без проектов (`REGISTRATION=open`); при `REGISTRATION=closed` зарегистрироваться самому нельзя. Если админа не осталось, задайте `ADMIN_LOGIN=<существующий логин>` в `.env` и перезапустите сервер; занять этот логин регистрацией нельзя.
- Новичок без проектов не видит ни других пользователей, ни администраторов.
- Пароли хранятся только в виде хэша bcrypt; участники их не видят. Хэширование идёт в отдельных потоках с ограниченной очередью: наплыв попыток входа или регистраций не останавливает сервер для остальных, а лишние запросы получают «Сервер перегружен».
- Свой пароль, двухфакторная аутентификация и активные сессии — кнопка «Безопасность» вверху страницы; админ сбрасывает пароль и 2FA в «Пользователях». При смене пароля остальные сессии пользователя закрываются, а пароль, выданный админом, пользователь меняет при первом входе.
- **Двухфакторная аутентификация** (TOTP: Яндекс Ключ, Google Authenticator и др.) с резервными кодами; политика `TWO_FACTOR` — по желанию, обязательно всем или только администраторам. **Политика паролей**: длина, виды символов, запрет популярных паролей и логина в пароле, срок действия, запрет повторов. **Сессии**: тайм-аут неактивности, лимит одновременных. Подробно — в [руководстве администратора](docs/ADMIN_GUIDE.md#политики-паролей-и-сессий-двухфакторная-аутентификация).
- Сессия — случайный токен в cookie `HttpOnly`, `SameSite=Lax`; через HTTPS cookie называется `__Host-tb_session` и получает флаг `Secure`: такую cookie не может подставить соседний поддомен, например чужой туннель на том же домене провайдера. В базе лежит только хэш токена.
- Ограничение попыток: 10 неудачных входов за 15 минут на логин с одного адреса, 30 — с одного адреса на любые логины, 50 — на один логин с любых адресов (перебор пароля не обойти сменой IP); 5 регистраций в час с адреса и 30 в час всего.
- Изменяющие запросы принимаются только с `Content-Type: application/json`, это защищает от подделки запросов с чужих сайтов. Загрузка файлов требует отдельный заголовок `X-Upload`, который чужой сайт отправить не может.
- Страница приложения отдаётся с `Content-Security-Policy`: браузер выполняет только код самого приложения. Через HTTPS ставится `Strict-Transport-Security`. Шрифты лежат в сборке, сторонних запросов нет.
- Токены для автотестов хранятся только в виде хэша и умеют только отправлять результаты: создать запуск, прислать результаты и файлы, завершить запуск. Читать и удалять с ними нельзя ничего. Отзываются во вкладке «Автотесты» → «Подключить автотесты».
- Вложения доступны только вошедшим пользователям. В браузере открываются только картинки и текст, остальное отдаётся на скачивание, и всё под заголовком `Content-Security-Policy: sandbox`: загруженный HTML или SVG не выполнится. Размер файла ограничен `MAX_UPLOAD_MB` в `.env` (по умолчанию 20 МБ).

- Секреты интеграций (токены трекеров и CI, секреты вебхуков) хранятся в базе зашифрованными AES-256-GCM; API их не возвращает. Настройки интеграций видят только тестировщики и администраторы проекта.

- **Журнал аудита**: «Пользователи» → «Журнал аудита» — входы и неудачные попытки, роли и доступы, удаления и восстановления, интеграции, токены, выгрузки; фильтры и выгрузка в CSV. Хранится `AUDIT_RETENTION_DAYS` дней (365).
- **Корзина**: удалённые тест-кейсы, прогоны и баги 30 дней (`TRASH_DAYS`) лежат во вкладке проекта «Корзина» и восстанавливаются целиком. Проект удаляет только администратор, подтвердив ключом; удалённый проект восстанавливается в «Пользователи» → «Удалённые проекты».


## Если что-то не работает

| Симптом | Что проверить |
|---|---|
| `docker: command not found` / `Cannot connect to the Docker daemon` | Docker Desktop не запущен или не установлен (шаг 1) |
| `Задайте POSTGRES_PASSWORD в файле .env` | Нет файла `.env` или в нём пустой пароль (шаг 3) |
| В логах `password authentication failed` | Пароль в `.env` поменяли после первого запуска. Верните прежний, либо, если данных ещё нет, `docker compose down -v` и запуск заново |
| `port is already allocated` | Порт 3002 занят. Задайте свободный `APP_PORT` в `.env` и перезапустите |
| Коллеги из локальной сети не открывают страницу | `APP_BIND=0.0.0.0` в `.env`, настройки брандмауэра, правильный IP, оба устройства в одной сети |
| «Неверный код установки» при регистрации первого пользователя | Код в логах: `docker compose logs app`, строка «Код для регистрации первого администратора». Он печатается, только пока в базе нет ни одного пользователя |
| «Регистрация закрыта» | `REGISTRATION=closed`: учётную запись создаёт админ в разделе «Пользователи» |
| «Слишком много попыток» / «Сервер перегружен» | Сработала защита от перебора и наплыва запросов. Подождите 15 минут (при «перегружен» — минуту) |
| Страница открывается, но «Связь с сервером прервана» | Посмотрите `docker compose logs app`; при работе через прокси проверьте, что он не буферизует ответы |
